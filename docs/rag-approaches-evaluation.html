Evaluation · GCF Q&A system · August 2026

Retrieval architectures for single- and multi-document answers

The system today runs single-shot dense retrieval: five 1,000-character chunks from a flat FAISS index feed one Claude call. That works for narrow factual lookups inside one document and structurally cannot serve comparison or aggregation queries across the corpus. This report evaluates the candidate approaches and recommends a staged path.

1 · What the corpus and queries actually demand

The corpus is Green Climate Fund board documents — funding proposal packages averaging roughly 200k tokens each, dense with identifiers (FP274, GCF/B.42/02), budget tables, country and sector names, and near-identical boilerplate sections repeated across every proposal. Two properties dominate the retrieval problem:

  • Identifier-heavy text. Users ask by proposal number, country, accredited entity, or board meeting. Dense embeddings are weak at exact codes; a 2021-era encoder (all-mpnet-base-v2) especially so.
  • Templated structure. Every proposal has the same section skeleton, so semantically similar chunks exist in all 90 documents. A global top-5 search for "expected mitigation impact" returns five near-duplicate paragraphs from whichever documents happen to score highest — not the one the user asked about.

An enterprise system has to serve four distinct query classes, and they fail differently today:

Query classExampleWhat happens today
Single-doc factual "What is the total GCF financing for FP274?" Works when the embedding lands on the right chunk; misses when the answer lives in a table split mid-row by the fixed-size chunker, or when the code "FP274" doesn't dominate the embedding.
Single-doc synthesis "Summarise the risk assessment of the Chad proposal." Five chunks ≈ 1,250 tokens is far too little context to synthesise a section that spans dozens of pages. Answers are thin or hallucinate structure.
Cross-doc comparison "Compare the adaptation components of FP270 and FP274." Global top-5 usually returns chunks from only one of the two documents (or neither). Nothing guarantees per-document coverage.
Corpus aggregation "Which proposals target West Africa, and what are their budgets?" Unanswerable by similarity search over chunks. Needs metadata filtering or corpus-level summaries; today it returns five arbitrary passages.

Two implementation-level gaps compound this, independent of architecture choice: follow-up queries are embedded raw ("what about its budget?" retrieves noise because the chat history is sent to Claude but never used to rewrite the retrieval query), and there is no relevance threshold — the top 5 are injected even when all scores are poor, inviting confident answers from irrelevant context.

2 · The approaches, evaluated

Tier A — Retrieval quality (fixes every query class at once)

Hybrid retrieval: BM25 + dense, fused with RRF Adopt

Run a lexical index (BM25) alongside the vector index and merge ranked lists with reciprocal rank fusion. For this corpus it is likely the single largest quality win: proposal codes, entity names, and monetary figures are exactly what lexical search nails and dense embeddings blur. Cost is minimal — rank-bm25 or a small SQLite FTS5 index over the same chunks, no new services, no re-embedding. Effectively no downside.

Structure-aware chunking Adopt

The current splitter cuts blindly every 1,000 characters, severing budget tables mid-row and headings from their bodies. The extracted markdown already carries the structure — split on headings, keep tables atomic, and prepend the section path ("FP274 › B.3 Financing information") to each chunk before embedding. This is a cheap version of Anthropic's contextual-retrieval result (~49% fewer retrieval failures when chunks carry situating context, ~67% combined with reranking). The full technique — an LLM writes a situating sentence per chunk — is affordable here as a one-off batch job (~18M tokens through Haiku at Batch API pricing is on the order of $10–15), but heading-path prefixes get most of the benefit for free.

Constraint: the grounded-viewer feature maps chunk text to page regions. Any chunking change requires re-running the grounding backfill, so batch these changes together.

Modern embedding model Adopt

all-mpnet-base-v2 (2021, 768-dim, 384-token input) trails current open models by a wide margin on retrieval benchmarks. BAAI/bge-m3 or intfloat/multilingual-e5-large run locally on the same sentence-transformers stack and handle longer inputs (8k tokens for bge-m3, which suits table-atomic chunks). A one-line config change (EMBEDDING_MODEL env var) plus a rebuild; the index config already records the model name, so old and new indexes coexist under data/index/<name> for A/B comparison.

Cross-encoder reranking Adopt

Retrieve top-30/50 with hybrid search, rerank with bge-reranker-v2-m3 (local, CPU-tolerable at this scale), keep the top 8–12. Rerankers read query and passage together, so they resolve exactly the ambiguity that kills bi-encoders on templated documents — distinguishing "mitigation impact of FP274" from the same paragraph in 89 other proposals. This also lets you raise the context budget: 10–12 reranked chunks (~4–6k tokens) is still cheap for Claude and materially improves synthesis answers.

History-aware query rewriting Adopt (bug-level fix)

Before retrieval, have the chat model condense the follow-up plus history into a standalone query ("what about its budget?" → "total budget of funding proposal FP274"). One cheap Haiku call, or a prompt-only instruction on the main call in a two-pass design. Without this, every follow-up question retrieves against an unresolvable pronoun.

Tier B — Multi-document capability (the enterprise requirement)

Document metadata + filtered retrieval Adopt

Build a small registry per document — proposal number, title, country/region, accredited entity, board meeting, sector, total financing — extracted once with Claude (the cover pages are templated, so this is a reliable batch job). Store it in chunks.jsonl metadata and a docs.json sidecar. This unlocks three things: scoped retrieval ("in FP274 …" filters chunks to that document before search), aggregation queries answered directly from the registry ("which proposals target West Africa" is a metadata lookup, not a retrieval problem), and per-document source labels in the UI. FAISS flat search doesn't filter natively, but at ~20–40k chunks a post-filter or per-doc sub-index is trivial.

Query decomposition + grouped retrieval Adopt

For comparison queries, one retrieval pass cannot serve two documents fairly. Have the model (or a rule on detected proposal codes) split "compare FP270 and FP274 budgets" into per-document sub-queries, retrieve top-k within each document, and assemble a sectioned context. Guaranteeing per-document quota is the point — it converts cross-doc comparison from "usually fails" to "works by construction". Pairs naturally with the metadata registry for resolving names ("the Chad proposal") to doc ids.

Two-stage retrieval: route to documents, then chunks Adopt (stage 2)

Embed a one-paragraph summary per document (generated once, batch). Stage 1 ranks documents; stage 2 searches chunks within the winners. With only ~90 documents the summaries even fit in the prompt directly, so document routing can be a single LLM classification instead of a second vector index. This kills the near-duplicate problem at its root — the templated sections of non-selected proposals never compete — and gives aggregation/summarisation queries a corpus-level surface to work from (the RAPTOR idea, at the depth this corpus actually needs).

Long-context reading with prompt caching Adopt selectively

Current Claude models take 1M tokens of context, and a whole proposal (~200k tokens) fits in one call. For deep single-document work — "walk me through the financial structure of FP274" — stuffing the routed document beats any chunk retrieval on answer quality. Prompt caching makes repeat questions against the same document ~90% cheaper, and the native citations feature (citations: {enabled: true} on a document block) returns passage-level cites that could feed the existing grounded viewer. Cost is the constraint: a cold 200k-token call is ~$0.60 at Sonnet input pricing versus well under a cent for a chunk-based answer, and latency rises accordingly. Use it as an explicit "deep dive" path after document routing, not the default.

Agentic retrieval (Claude drives a search tool) Adopt for hard queries (stage 3)

Give Claude a search_corpus(query, doc_filter?) tool (plus list_documents over the registry) and let it iterate: search, read, refine, search again. This is the highest-ceiling option — it handles multi-hop questions no single retrieval pass can ("which proposals share an accredited entity with FP270, and how do their grant terms differ?") and degrades gracefully to one tool call for simple lookups. Costs are 2–6× the latency and tokens of single-shot RAG and the answer pipeline becomes a loop (the SDK tool-runner handles this). The right posture: route to it when decomposition detects a complex query, keep single-shot for the rest.

Tier C — Heavy machinery

GraphRAG / knowledge graph Skip for now

Entity-relation graphs pay off when queries traverse many-hop relationships across thousands of documents. Here, the metadata registry plus document routing covers the realistic aggregation queries at a fraction of the build and maintenance cost. Revisit only if users demand thematic corpus-wide analysis ("how has GCF's treatment of indigenous peoples' safeguards evolved across board meetings?") often enough to justify it.

ColBERT / late-interaction, fine-tuned embeddings Skip

Late-interaction models and domain-fine-tuned embedders chase the same gains hybrid + reranking already capture, with a much heavier serving stack (per-token vectors, custom index) or a training pipeline you'd have to maintain. Not warranted at 90 documents.

4 · How to know it worked: the evaluation harness

"Great answers" needs a measurement, or every change is a guess. Before changing the pipeline, build a small gold set — this is also the deliverable that makes the comparison defensible in the project report:

  • 50–80 questions spread across the four query classes, each with the expected answer and the ground-truth document/pages (the page-aware index makes labelling easy).
  • Retrieval metrics, judged without the LLM: recall@k and MRR against the labelled pages. This isolates whether a change helped retrieval before any generation noise enters.
  • Answer metrics via LLM-as-judge (a fixed judge model scoring correctness and faithfulness against the gold answer and retrieved context), plus citation accuracy — did the cited doc/page actually contain the claim? The grounding machinery already computes exactly this mapping.
  • Run it as a script over each index/config so default vs hybrid-rerank vs routed becomes one table. The Batch API halves the judging cost.

5 · Recommended path

1

Retrieval foundation (~1 week, no architecture change)

Eval harness first. Then structure-aware chunking + heading-path context, modern embedder, hybrid BM25+dense with RRF, reranker to top-10, score threshold, and history-aware query rewriting. Re-run the grounding backfill once at the end. This tier alone should transform single-document quality and is prerequisite plumbing for everything else.

2

Multi-document capability (~1 week)

Metadata registry (batch-extract once), document routing, query decomposition with per-document retrieval quotas, and registry-answered aggregation queries. This is the stage that delivers the stated enterprise requirement — queries spanning one to many documents.

3

High-ceiling paths, routed by query type (optional, after measuring stage 2)

Long-context deep-dive mode for single-document analysis (with prompt caching and native citations feeding the grounded viewer), and an agentic search loop for the multi-hop queries that decomposition flags as complex. Only build what the eval numbers say is still failing.

Bottom line. No single "advanced RAG" swap wins here. The corpus (few, huge, templated, identifier-dense documents) rewards a layered design: hybrid + reranked retrieval as the floor, metadata and document routing as the multi-document mechanism, and agentic / long-context modes reserved for the queries that need them. GraphRAG and custom embedding training are not justified at this scale.
Operational notes. The LM Studio single-concurrency limit only affects VLM extraction, not the answer path (which uses the Anthropic API). All Tier-A components (BM25, embedder, reranker) run locally, so per-query cost stays dominated by the one Claude call.

Retrieval architectures for single- and multi-document answers

The original dense-only baseline has been replaced by identifier-aware hybrid retrieval, query decomposition, a metadata registry, confidence handling, and grounded citations. Document recall is now strong; the remaining work is evidence precision and answer correctness inside the right document.

Current checkpoint. Hybrid retrieval scores 100% recall@5 and MRR 1.00 on the 30-question English retrieval set across identifier, board-code, and paraphrase classes. Dense-only scores 30% overall. The default index has no exact duplicate rows. These results establish that the dominant failure has moved from wrong document to wrong page, incomplete evidence, or unsupported synthesis.

1 · What the corpus and queries actually demand

The corpus is Green Climate Fund board documents, dense with identifiers (FP274, GCF/B.42/02), budget tables, country and sector names, and near-identical boilerplate repeated across proposals. Three properties now dominate the remaining problem:

  • Templated facts. Fields such as A.7, A.8, and A.11 should be resolved as structured facts with page provenance, not rediscovered probabilistically for every answer.
  • Page and section structure. Fixed-size chunks can detach table values from headings, units, baseline/target columns, and neighboring contradictory values.
  • Evidence use. Finding the correct document does not ensure that the generator selects the canonical page, covers every requested field, or limits each claim to what its citation entails.

An enterprise system has to serve four distinct query classes. The hybrid and registry work changed their failure modes, but each still has a distinct remaining risk:

Query classExampleCurrent behavior and remaining risk
Single-doc factual "What is the total GCF financing for FP274?" Hybrid retrieval and identifier resolution reliably reach the document. Fixed-size chunks can still separate a value from its heading, units, or canonical table, leaving the answer model to choose among incomplete evidence.
Single-doc synthesis "Summarise the risk assessment of the Chad proposal." The larger context budget improves coverage, but there is no section expansion or reranker. Long sections can still be represented by disconnected passages, producing thin or weakly supported summaries.
Cross-doc comparison "Compare the adaptation components of FP270 and FP274." The conductor decomposes explicit identifiers and round-robin assembly gives each document a quota. Completeness is not yet guaranteed for every requested document × field pair.
Corpus aggregation "Which proposals target West Africa, and what are their budgets?" The registry handles simple proposal, year, country, and financing lookups. Broader sector or region questions remain limited by missing fields, normalization, provenance, and conflict handling.

The original implementation-level gaps — raw follow-up retrieval and unconditional context injection — are now addressed by the conductor and confidence guard. New reviews exposed the next gaps: factual answer generation still receives prior assistant history, citation checks validate page presence rather than claim support, and the registry lacks field-level provenance and conflict representation.

2 · The approaches, evaluated

Tier A — Retrieval quality (fixes every query class at once)

Hybrid retrieval: BM25 + dense, fused with RRF Implemented

The current SQLite FTS5 and dense indexes are fused with reciprocal rank fusion. On the 30-question retrieval evaluation, hybrid search reaches 100% recall@5 and 1.00 MRR versus 30% recall@5 and 0.28 MRR for dense-only retrieval. The tradeoff is measurable latency: 139 ms/query versus 32 ms/query in the recorded run, which is acceptable for now and should remain visible in regression tests.

Structure-aware chunking Next

The current splitter cuts every 1,000 characters, which can separate budget-table values from row labels and headings from their bodies. Split on document headings, keep tables atomic where practical, and add the section path to a separate retrieval_text field. Preserve the verbatim passage as source_text for prompts, citations, and the grounded viewer.

Constraint: any chunking change requires an index rebuild and grounding backfill. Version the chunk schema and run the old and new indexes side by side until answer-level evaluation supports the migration.

Modern embedding model Measure first

all-mpnet-base-v2 (2021, 768-dim, 384-token input) trails current open models by a wide margin on retrieval benchmarks. BAAI/bge-m3 or intfloat/multilingual-e5-large run locally on the same sentence-transformers stack and handle longer inputs (8k tokens for bge-m3, which suits table-atomic chunks). A one-line config change (EMBEDDING_MODEL env var) plus a rebuild; the index config already records the model name, so old and new indexes coexist under data/index/<name> for A/B comparison.

Cross-encoder reranking Next

Retrieve a wider hybrid candidate set, rerank with a cross-encoder such as bge-reranker-v2-m3, and keep the best 8–12 passages. Reading the query and passage together should help distinguish a field for FP274 from the same templated field in many other proposals. Benchmark CPU latency and answer quality before enabling it by default.

History-aware query rewriting Implemented

The conductor now condenses follow-ups into standalone retrieval queries and resolves explicit proposal identifiers. The remaining correctness issue is downstream: prior assistant turns are still included in final answer generation, so retrieved evidence and conversational continuity need separate inputs and precedence rules.

Tier B — Multi-document capability (the enterprise requirement)

Document metadata + filtered retrieval Partial

The current data/registry.json contains 273 documents and resolves proposal identifiers, titles, accredited entities, countries, years, and some financing fields. The next schema must retain page-level provenance, extraction method and confidence, normalized values, and conflicting candidates. That turns registry answers from convenient shortcuts into auditable evidence.

Query decomposition + grouped retrieval Partial

For comparison queries, one retrieval pass cannot serve two documents fairly. Have the model (or a rule on detected proposal codes) split "compare FP270 and FP274 budgets" into per-document sub-queries, retrieve top-k within each document, and assemble a sectioned context. Guaranteeing per-document quota is the point — it converts cross-doc comparison from "usually fails" to "works by construction". Pairs naturally with the metadata registry for resolving names ("the Chad proposal") to doc ids.

Two-stage retrieval: route to documents, then chunks Partial

Explicit proposal identifiers already route retrieval to document-scoped searches. A broader first-stage router based on registry fields or document summaries may help name-based and thematic questions, but it should be added only after the answer-level benchmark shows unresolved document-selection errors.

Long-context reading with prompt caching Adopt selectively

Some model providers support whole-document contexts, prompt caching, and native citations. This may be useful for deep single-document work, but the current OpenAI-compatible deployment needs its own quality, cost, latency, and citation-grounding benchmark. Keep it as an explicit deep-dive experiment after document routing, not the default path.

Agentic retrieval (model-driven search loop) Adopt for hard queries (stage 3)

Expose search_corpus(query, doc_filter?) and list_documents tools so the answer model can search, inspect evidence, refine, and search again. This can handle multi-hop questions that defeat one retrieval pass, but it increases latency, token use, and evaluation complexity. Consider it only after deterministic field planning and claim verification are reliable.

Tier C — Heavy machinery

GraphRAG / knowledge graph Skip for now

Entity-relation graphs pay off when queries traverse many-hop relationships across thousands of documents. Here, the metadata registry plus document routing covers the realistic aggregation queries at a fraction of the build and maintenance cost. Revisit only if users demand thematic corpus-wide analysis ("how has GCF's treatment of indigenous peoples' safeguards evolved across board meetings?") often enough to justify it.

ColBERT / late-interaction, fine-tuned embeddings Skip

Late-interaction models and domain-fine-tuned embedders chase many of the gains hybrid search and reranking already capture, with a much heavier serving stack or training pipeline. They are not warranted at the current corpus scale without evidence from the answer-level benchmark.

4 · How to know it worked: the evaluation harness

The existing harness proves document retrieval, but it cannot distinguish a correct answer from a hallucination generated from the correct document. Extend it rather than replacing it:

  • 50–80 questions across identifier, semantic, comparison, contradiction, multilingual, noisy-input, and unanswerable classes.
  • Document and page retrieval metrics: recall@k, MRR, per-document coverage, and evidence-page recall.
  • Deterministic answer checks: required-field coverage, arithmetic, currency compatibility, identifier conflicts, and abstention accuracy.
  • Claim checks: each atomic claim classified as supported, contradicted, or unsupported by its cited page; track citation precision and completeness separately.
  • Conversation checks: rerun the same question after unrelated turns to detect history contamination.

5 · Recommended path

1

Measure answer correctness (next)

Promote the complex manual probes into an answer-level regression suite with exact pages, expected fields, conflict outcomes, and abstentions. Freeze current hybrid metrics as the retrieval baseline.

2

Build an evidence-first answer path (core work)

Isolate factual generation from prior assistant answers; add provenance-aware structured facts, section/page expansion, deterministic document × field planning, and cross-encoder reranking. Preserve contradictions rather than normalizing them away.

3

Verify and selectively escalate (after core work)

Check each generated claim against its cited evidence and repair or abstain once. Consider a modern embedder, vision verification for difficult tables, long-context reading, or agentic search only where the expanded evaluation still shows a measurable gap.

Bottom line. The hybrid and routing foundation is working. The next milestone is not another broad architecture swap; it is a verifiable evidence contract from document fields and sections through to answer claims. See RAG correctness: next implementation steps for the executable plan.
Operational notes. The answer path currently uses an OpenAI-compatible chat client and gpt-4o-mini by default.

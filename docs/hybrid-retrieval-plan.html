Hybrid retrieval: BM25 + dense with rank fusion

The single highest-impact change identified in the retrieval evaluation: run a lexical BM25 index alongside the existing FAISS dense index and merge the two ranked lists with Reciprocal Rank Fusion. This document explains the mechanism in full, then lays out a step-by-step plan mapped to the actual modules in src/gcf_qna/rag/.

User query→ History-aware rewrite→ Dense search (FAISS) · top 30 BM25 search · top 30 → RRF fusion→ Top 5–10 chunks→ Claude + grounded citations

Part I — Why this is the biggest win

1. The failure mode of dense-only retrieval on this corpus

The current retriever embeds the query with all-mpnet-base-v2 and returns the five nearest chunks by cosine similarity. Embeddings encode meaning as a direction in vector space — and that representation has a structural blind spot: rare, exact tokens carry almost no weight.

Typical queries against this corpus lean on exactly those tokens: FP274, GCF/B.42/02, an accredited entity's name, a country, a dollar figure. To the embedding model, FP274 is a low-frequency alphanumeric string it has essentially never seen in training; it contributes a tiny, noisy nudge to the 768-dimension vector, while the surrounding words — "total financing for" — dominate it.

The corpus shape turns this weakness into the dominant failure mode. All ~90 funding-proposal packages follow the same template, so every document contains a near-identical "financing information" section written in the same GCF boilerplate. The query vector for "total financing for FP274" therefore lands in a dense cloud of interchangeable chunks from every proposal, and the top 5 are whichever documents' boilerplate happens to score highest — frequently not FP274's. The one token that uniquely identifies the correct document is precisely the token the embedding ignores.

Two consequences make this the most damaging error class in an enterprise setting:

  • Wrong-document answers look right. Another proposal's financing section is fluent, plausible, and confidently cited. A user who doesn't cross-check the source images is misled, not merely unserved.
  • No downstream stage can recover. A reranker, a better prompt, a stronger chat model — none of them can surface a chunk that retrieval never returned. Candidate recall is the ceiling on everything else.

2. What BM25 contributes

BM25 is the classic lexical ranking function (the default scorer in Lucene/Elasticsearch). It scores a chunk against a query by exact term overlap, shaped by three factors:

  • Inverse document frequency (IDF). Rare terms score enormously; common terms score near zero. FP274 appears in one document's chunks → huge IDF → any chunk containing it rockets to the top of the list. "Financing" appears everywhere → contributes almost nothing. This is exactly the inverse of the embedding's behaviour: BM25 is strongest precisely where dense retrieval is weakest.
  • Term-frequency saturation. A chunk mentioning a term three times beats one mentioning it once, but with sharply diminishing returns — so repetitive boilerplate cannot win on volume.
  • Length normalisation. Long chunks don't win simply by containing more words.

BM25's own blind spot is the mirror image: it needs the literal words. Ask "how does the project handle drought resilience?" when the document says "adaptation to water scarcity" and BM25 finds nothing — while the embedding handles the paraphrase easily. Neither retriever subsumes the other, which is why the design runs both.

3. Reciprocal Rank Fusion

Every query now yields two ranked lists whose raw scores are incomparable — cosine similarity in [0, 1] versus unbounded BM25 scores. RRF sidesteps score calibration entirely by using only ranks:

RRF(chunk) = Σ over each list containing the chunk of   1 / (k + rank)     with k ≈ 60

The constant k damps the influence of top positions so a single list cannot dominate. A chunk ranked #2 by dense and #5 by BM25 scores 1/62 + 1/65 ≈ 0.0315, beating a chunk ranked #1 in one list but absent from the other (1/61 ≈ 0.0164). Three properties fall out:

  • A chunk that both retrievers like — semantically on-topic and carrying the query's identifiers — is almost guaranteed a top slot. That is usually the correct answer chunk.
  • Each retriever can still surface results the other missed entirely, preserving coverage on purely semantic and purely lexical queries alike.
  • There is nothing to tune or normalise. In the IR literature RRF sits within a hair of far more elaborate fusion methods, which is why it is the standard choice in production systems.

A concrete trace for "total GCF financing for FP274":

RetrieverWhat its top results look likeOutcome

4. Impact-per-effort, summarised

  • Attacks the dominant failure mode — wrong-document retrieval — rather than polishing ranking quality at the margins.
  • Nearly free. Pure-Python lexical index over the exact chunks already in chunks.jsonl. No new services, no GPU, no re-embedding, no API cost. Millisecond query overhead.
  • No trade-off to manage. Worst case, BM25 adds noise on a purely semantic query, and RRF's rank damping filters most of it.
  • Multiplies later stages. A cross-encoder reranker can only reorder the candidate pool; hybrid fixes the pool (recall), the reranker then fixes the order (precision). This is why hybrid comes first in the roadmap sequencing.
  • No grounding backfill required. Chunk text is unchanged, so the chunk→page-region mapping behind the grounded viewer is untouched — unlike the chunking changes, which do force a backfill.

Part II — Implementation plan

Sequenced so each step is independently verifiable. Steps 1–4 are the core; steps 0 and 6 bracket the work with measurement. Nothing here changes chunk content, the index-on-disk contract for existing indexes, or the app's Hit interface — the Chainlit app and the grounding pipeline are untouched consumers.

0

Baseline measurement ½ day

Before touching retrieval, freeze a small gold set: 25–40 questions with known answer locations, deliberately weighted toward identifier queries ("…for FP274", "…in GCF/B.30/02/Add.11", entity and country names) plus a handful of paraphrase questions where dense should win. Each entry: question → expected doc_id (+ page where easy). A script (scripts/eval_retrieval.py) runs the current retriever and reports recall@5 / recall@10 (did any returned chunk come from the right document?) and MRR. This baseline is the before/after evidence for the whole change.

1

Tokenizer for identifier-heavy text ½ day

BM25 lives or dies on tokenization here. Requirements:

  • FP274 survives as one token (and, ideally, also emits fp+274-joined variants so "FP 274" matches).
  • Board codes like GCF/B.42/02/Add.16 split on / but keep meaningful pieces (b.42, add.16) intact.
  • Lowercase everything; strip punctuation except intra-token . and digits; keep numbers (budget figures are searchable signal).

Sketch (new module src/gcf_qna/rag/lexical.py):

TOKEN_RE = re.compile(r"[a-z0-9]+(?:\.[a-z0-9]+)*")

def tokenize(text: str) -> list[str]:
    return TOKEN_RE.findall(text.lower())

Also index each chunk's doc_id text alongside its body — filenames like 02_gcf-b42-02-add16-funding-proposal-package-fp274 carry the proposal number even when the chunk body doesn't. Concatenating doc_id.replace("-", " ") into the indexed text is a one-line, high-yield trick.

Unit tests: tokenize("FP274")==["fp274"], codes in real corpus samples round-trip, no empty-token output.

2

Build and persist the BM25 index ½–1 day

Two viable backends; recommendation is the first:

OptionForAgainst
rank-bm25 (pure Python)~20 lines; zero infrastructure; index = pickled token lists or rebuilt from chunks.jsonl at load (seconds at this scale)Whole index in memory (fine at ≤ 40k chunks); pickle sidecar is the one non-JSON artifact — or avoid it by re-tokenizing at load
SQLite FTS5Persistent, queryable, no pickle; scales furtherFTS5 default tokenizer will split codes — needs a custom tokenizer or pre-tokenized column; more moving parts

With rank-bm25, prefer rebuilding from chunks.jsonl at load time over persisting a pickle: it keeps the on-disk index format exactly as it is today (JSON + FAISS only, the deliberate no-pickle contract in index.py), costs a few seconds at startup, and guarantees the lexical index can never drift from the chunk metadata. Record "lexical": "bm25-okapi + tokenizer-v1" in config.json so indexes are self-describing.

Touchpoints: lexical.py (new), index.py (config field), scripts/build_index.py (no structural change — chunks are unchanged).

3

Fusion in the retriever ½ day

Extend Retriever.search() to query both indexes deep (top 30 each — fusion needs overlap room), fuse by rank, and return the same Hit list as today so every consumer (context assembly, sources line, grounding) is untouched:

def rrf(ranked_lists: list[list[int]], k: int = 60) -> dict[int, float]:
    scores: dict[int, float] = {}
    for ranking in ranked_lists:
        for rank, idx in enumerate(ranking):
            scores[idx] = scores.get(idx, 0.0) + 1.0 / (k + rank + 1)
    return scores

def search(self, query: str, top_k: int = 5) -> list[Hit]:
    dense_ids = self._dense_ranking(query, n=CANDIDATES)     # existing FAISS path
    lex_ids   = self._lexical_ranking(query, n=CANDIDATES)   # BM25 path
    fused = sorted(rrf([dense_ids, lex_ids]).items(),
                   key=lambda kv: kv[1], reverse=True)[:top_k]
    return [self._hit(idx, score) for idx, score in fused]

Keep the existing FAISS -1-padding guard inside _dense_ranking. Report the RRF score in Hit.score (documented as a rank-fusion score, not cosine) — the app only formats it, so nothing breaks; the score-threshold guard (step 4) then operates on ranks/scores consistently.

Config additions in config.py, all env-overridable per the repo's convention: CANDIDATES_PER_RETRIEVER=30, RRF_K=60, HYBRID=1 (kill-switch back to dense-only for A/B).

4

No-answer guard hours

Today the top 5 are injected regardless of quality. Add a floor: if the best fused result's underlying signals are weak (e.g. best cosine below a threshold and no lexical hit contained a rare query term), prepend a note to the context telling the model retrieval confidence is low. The system prompt already instructs "say so plainly instead of guessing" — this gives that instruction the signal it needs to fire.

5

Companion fix: history-aware query rewriting ½ day

Hybrid cannot fix follow-ups — "what about its budget?" gives BM25 no identifier to latch onto either, since the pronoun is unresolvable by both retrievers. In chainlit_app.py, before calling retriever.search(), make one small Claude Haiku call: given the last few history turns and the new message, emit a standalone search query ("total budget of funding proposal FP274"). Use the rewritten query for retrieval only; send the user's original message to the main model as before. Skip the call when there is no history.

6

Measure, A/B, adopt ½ day

Re-run eval_retrieval.py from step 0 against dense-only (HYBRID=0) and hybrid. Acceptance criteria: recall@5 on identifier questions improves substantially (expectation: from roughly coin-flip to near-ceiling), recall on paraphrase questions does not regress beyond noise, and per-query latency overhead stays under ~50 ms. Then flip the default and record both numbers — they are the headline result for the project report.

Testing checklist

  • Tokenizer unit tests: codes survive, casing, punctuation, numerals, empty input.
  • RRF unit tests: deterministic ordering, both-lists beats single-list at comparable ranks, ties broken stably.
  • Retriever integration: hybrid returns valid Hits on the real index; HYBRID=0 reproduces current behaviour byte-for-byte; tiny-index edge case (fewer chunks than top_k) still respects the -1-padding guard.
  • End-to-end smoke: the two canonical queries — one identifier-led, one paraphrase-led — through the Chainlit app, confirming sources cite the expected document and grounded page images still render.

Rollout & risk

  • Zero-risk rollout path: the change is code-side only; existing indexes remain valid. Ship behind HYBRID=1, keep the env kill-switch for one iteration, delete it once the eval numbers are in.
  • Known residual gaps (by design, addressed later in the roadmap): follow-up resolution beyond simple rewrites, per-document quotas for comparison queries (stage 2 decomposition), and ranking precision within the right document (reranker).
  • Failure mode to watch: BM25 over-rewarding chunks that merely mention a proposal code in cross-references ("as in FP198…"). The reranker planned next in Tier A is the systematic fix; in the interim the fused dense signal keeps these from dominating.
Definition of done. Gold-set recall@5 for identifier queries materially improved and documented; paraphrase recall not regressed; HYBRID default on; follow-up questions retrieve against rewritten standalone queries; grounded viewer unchanged and verified working.
Effort summary: roughly 3–4 focused days including evaluation, all local, no new services, no API-cost increase beyond one small rewrite call per follow-up turn. No grounding backfill needed — chunk text is untouched.
